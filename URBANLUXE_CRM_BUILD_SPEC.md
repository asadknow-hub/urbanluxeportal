# UrbanLuxe CRM — Lead · Deal · Customer
### Phased Build Specification for an AI Code Agent

**Product:** UrbanLuxe Real Estate — sales CRM
**Scope of THIS build:** Lead capture → Customer → Qualification → Deal pipeline → Viewings → Deal outcome. A focused sales CRM, **not** property management / ERP.
**Currency:** AED only (see §B).
**Stack:** Next.js (Vercel) · Supabase (Postgres + Auth + Storage + RLS).
**How to use this doc:** build **one phase at a time, in order**. Each phase is self-contained — its tables, enums, relationships, RLS policies, automations, and a Definition-of-Done checklist are all inside that phase. Do not start a phase until the previous phase's checklist passes.

---

## A. Instructions for the build agent

1. Build phases **strictly in order (1 → 6)**. Each phase lists `Depends on:` — those must already exist.
2. Apply the **Global Conventions (§B)** to every table in every phase. They are stated once and never repeated.
3. Every table = one Supabase migration file. Name migrations `NN_phaseN_tablename.sql`.
4. Enums are created in the phase where they first appear. The full list is consolidated in §E for reference — but create each enum the first time its phase needs it.
5. At the end of each phase, verify the **Definition of Done** checklist before moving on.
6. Anything in **§D (Deferred)** must **not** be built now. The schema is intentionally shaped to accept it later — do not add those columns/tables.
7. When a spec says `[derived]` build it as a Postgres view/function — never store the value.
8. When a spec says `[config]` it is admin-editable reference data — build a seed migration with the listed default rows.

## B. Global conventions (apply to every table)

### B.1 Common columns — every table inherits these unless it says *(append-only)*
| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `default gen_random_uuid()` |
| `created_at` | `timestamptz` | `default now()` |
| `updated_at` | `timestamptz` | trigger-maintained (`set_updated_at()`) |
| `created_by` | `uuid` FK → `app_user` NULL | null for system/import rows |
| `updated_by` | `uuid` FK → `app_user` NULL | |
| `deleted_at` | `timestamptz` NULL | **soft delete**; every query filters `deleted_at is null` |

### B.2 Money — **AED only**
All monetary columns are `numeric(14,2)` and represent **AED**. **Do not** store a currency column anywhere. If multi-currency is ever needed it becomes a future migration (out of scope now).

### B.3 Human-readable codes
High-value entities carry a short `*_code` generated by a dedicated Postgres sequence, alongside the uuid PK: `CUST-00001`, `OPP-1043`, `PROP-00877`, `USR-014`. Build one `code_sequence` helper + per-entity sequences.

### B.4 Custom fields
Every major entity has `custom_fields jsonb default '{}'`. Admin-defined field definitions live in `custom_field_def` (built in Phase 6). This lets admins add dropdowns/fields without schema changes.

### B.5 Polymorphic links
Cross-cutting records (`document`, `activity_timeline`, `follow_up`, `task`, `note`) attach to any entity via the pair `(related_to_type entity_type, related_to_id uuid)`. Everything else uses explicit FKs.

### B.6 RLS — enforced in Postgres from Phase 1
- `agent` → rows where `assigned_user_id = auth.uid()` or unassigned in their team pool.
- `team_lead` / `manager` → all rows for their `team_id`.
- `admin` → everything. `viewer` → read-only.
- Reference/`[config]` tables: read-all, write-admin.
Each ownable table exposes `assigned_user_id`; RLS policies read it.

### B.7 Audit
`audit_log` (Phase 2) is trigger-populated on all customer/deal/transaction tables. Append-only, never soft-deleted.

### B.8 Ordering
Board entities (`opportunity`) carry `position numeric` for drag-order within a kanban column.

# PHASE 3 — Leads & Customers

**Goal:** Capture leads from configurable sources, auto-assign them, and hold one master record per person/company that flows from lead → client without changing rows.
**Depends on:** Phases 1–2.

| `channel` | enum `lead_channel` | |

### Automations (basic version — full engine in Phase 6)
- **Lead assignment:** on `customer` insert with `status=lead`, resolve `assigned_user_id` from the source's `assignment_rule` (`round_robin` / `load_balanced` across the team; `fixed` → `default_assignee_id`).

- Attach `audit_row()` to `customer`.

### RLS
- `customer`, `customer_kyc`, `lead_qualification`: scoped by `customer.assigned_user_id` per §B.6.
- `customer_kyc` additionally restricted so only `admin`/`manager`/owning agent read it.

- [ ] A new website-form lead creates a `customer(status=lead)`, gets auto-assigned, spawns a follow-up + notification.
- [ ] Same row's `status` can move to `qualified` → `active_client` without creating a new record.
- [ ] Lead-source attribution is queryable (count of customers per source).
- [ ] An agent cannot see another team's customers (RLS).

- `opportunity` and children scoped by `opportunity.assigned_user_id` per §B.6.

- [ ] Properties can be shortlisted onto a deal and a viewing scheduled + outcome recorded.
- [ ] Winning a deal updates the customer to `active_client` and stamps `client_since`.
- [ ] Losing a deal enforces a lost reason.
- [ ] Pipeline value per stage and per agent is queryable.

## C. Pragmatic AI (optional, after Phase 6 — schema-safe, no migrations)

Add only if they remove real manual work; skip generic chatbots:
1. **Lead scoring** — set `customer.rating` from source + budget fit + engagement, to sort the follow-up queue.
2. **Smart property matching** — rank `listing` against a `lead_qualification` profile; auto-fill `opportunity_property(role=suggested)`.
3. **Duplicate lead detection** — fuzzy match on mobile/email/WhatsApp before creating a `customer`.
4. **Document OCR** — extract passport / Emirates ID fields to pre-fill `customer_kyc`.

Each is an external service that only reads/writes existing tables.

## D. Deferred — DO NOT BUILD NOW

Out of scope for this CRM build. The schema is shaped to accept these later (e.g. `property` is the canonical asset so ownership/tenancy can attach without refactoring), but **do not create these tables or columns now**:

- **Property management & operations:** `property_management`, `maintenance_request`, owner statements.
- **Rentals:** `tenancy`, `rental_history`, Ejari lifecycle.
- **Portfolio / ownership:** `property_ownership`, `mortgage`, estimated equity / portfolio valuation.
- **Full finance/billing:** `invoice`, `invoice_line`, `payment_received`, `quotation`, payment plans / installments.
- **Multi-currency:** everything is AED (§B.2).
- **AML/PEP/sanction screening:** KYC in Phase 3 stores identity docs only; screening fields are a future compliance phase.
